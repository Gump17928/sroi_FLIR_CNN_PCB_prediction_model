1. ORIGINAL PROBLEM
================================================================================

SYMPTOM:
--------
Model trained on HBridge PCB with component-level holdout validation shows:
- R² = -3.46 (worse than baseline)
- RMSE = 9.89°C
- Predictions highly correlated with FLIR input (r=0.993)
- Predictions poorly correlated with ground truth (r=0.146)

DIAGNOSTIC EVIDENCE:
--------------------
Comprehensive analysis revealed:
1. Predictions vs FLIR input:     r = 0.993 → Model COPYING input
2. Predictions vs Ground truth:   r = 0.146 → Model NOT learning target
3. FLIR vs Ground truth:          r = 0.131 → There IS a transformation to learn

CONCLUSION: Model is outputting FLIR surface temps, not embedded temps

ROOT CAUSE:
-----------
The model architecture and training setup creates a fundamental learning problem:

A) Sparse Supervision (Masked Loss)
   - Only 22 component ROIs supervised (~1,800 pixels out of 307,200)
   - 99.4% of pixels receive no gradient signal
   - Model learns: "output temps at these specific pixel locations"
   - Model does NOT learn: "transform local FLIR pattern → embedded temp"

B) Component-Level Holdout (Spatial Validation)
   - Training: 18 components (locations: L1, L2, ..., L18)
   - Validation: 4 components (locations: V1, V2, V3, V4)
   - Validation locations NEVER receive gradients during training
   - Model defaults to FLIR-like output at unseen locations

C) Location-Specific Learning
   - Model learns: "At pixel (x,y), predict temperature T"
   - Model learns global image → specific pixel mappings
   - Model does NOT learn: "Local FLIR pattern → embedded offset"
   - No spatial translation invariance

ANALOGY: 
--------
It's like teaching someone to predict indoor temperature from outdoor temperature,
but only training them on houses at specific GPS coordinates. When you ask them
to predict for a house at a new location, they just repeat the outdoor temp
because they never learned the general indoor/outdoor relationship.

6. EXPECTED ISSUES WITH OPTION 1
================================================================================

ISSUE 1: Location-Specific Learning (CRITICAL)
-----------------------------------------------
Problem:
  Model learns: "At pixel coordinates (x,y), predict temperature T"
  Not: "Given local FLIR pattern, predict embedded offset"

Why It Happens:
  - U-Net architecture processes full image with spatial awareness
  - Masked loss provides supervision at specific pixel locations
  - Model implicitly learns to use absolute position as feature
  - Convolutional layers can encode position via receptive field

Evidence:
  - Model works on training locations (HBridge ROIs)
  - Model fails on validation locations (LoadShedding ROIs)
  - Even though FLIR patterns may be similar

Impact on Cross-PCB:
  - LoadShedding components at different (x,y) positions
  - Model never trained at those positions
  - Defaults to FLIR-like output


ISSUE 2: Different PCB Characteristics
---------------------------------------
Problem:
  HBridge ≠ LoadShedding in many ways

Differences:
  1. Component types (different ICs, passives)
  2. Power dissipation patterns
  3. Board geometry and layout
  4. Thermal coupling between components
  5. Heat sinking effectiveness
  6. Component densities
  7. Trace routing (affects thermal paths)

Impact:
  Even if model learned generalizable features, physics differs
  
Example:
  - HBridge: High-power MOSFET, embedded temp = FLIR + 15°C
  - LoadShedding: Low-power IC, embedded temp = FLIR + 2°C
  - Model trained on HBridge offset won't apply to LoadShedding


ISSUE 3: Insufficient Training Diversity
-----------------------------------------
Problem:
  Training on 1 PCB design = limited pattern diversity

Statistics:
  - 1 PCB × 185 timestamps ≈ 185 unique thermal conditions
  - 22 components × 185 timestamps = 4,070 training samples
  - But all from SAME spatial configuration

Comparison to Typical CNN Training:
  - ImageNet: 1.2M images, diverse scenes
  - Our case: 185 thermal states, 1 PCB layout
  - Insufficient to learn generalizable physics

Impact:
  Model overfits to HBridge-specific patterns
  Cannot extrapolate to LoadShedding


ISSUE 4: Sparse Supervision Prevents Local Learning
----------------------------------------------------
Problem:
  Masked loss only penalizes 22 ROIs (~0.6% of pixels)

Consequence:
  - Model doesn't learn local FLIR pattern → temp relationship
  - No gradient signal for most of the image
  - Intermediate layers don't learn useful local features
  - Model learns global image → specific outputs

What We Need:
  Model should learn: "In 16×16 patch around component, FLIR pattern → embedded offset"

What We Get:
  Model learns: "Given full 480×640 image, output temps at these 22 locations"


ISSUE 5: No Spatial Translation Invariance
-------------------------------------------
Problem:
  Same component at different locations treated as different

Example:
  - Component A at HBridge position (100, 200)
  - Same component type at LoadShedding position (250, 350)
  - Model should predict same FLIR→embedded relationship
  - But model treats these as unrelated

Cause:
  - U-Net uses position information implicitly
  - No mechanism to enforce translation invariance
  - Masked loss doesn't encourage position-independent learning

7. METHODS TO FIX THE FUNDAMENTAL PROBLEMS
================================================================================

FIX 1: Dense Supervision via Interpolation
-------------------------------------------
Concept:
  Generate dense ground truth across full image, not just ROIs

Method 1A: Physics-Based Interpolation
  - Use thermal diffusion equation
  - Interpolate from known ROI temperatures
  - Account for heat sources, sinks
  - Creates smooth temperature field

Implementation:
  1. For each frame, have 22 point measurements
  2. Solve thermal diffusion: ∇²T = heat_sources
  3. Boundary conditions: ROI temps, board edges
  4. Output: Full 480×640 temperature map
  5. Train with pixel-wise MSE loss (not masked)

Pros:
  + Every pixel receives gradient signal
  + Model learns local patterns everywhere
  + Can generalize to new positions

Cons:
  - Interpolation may not be accurate
  - Requires physics model parameters
  - Computationally intensive
  - Assumes smooth thermal field (may not be true)


Method 1B: Neural Interpolation
  - Train auxiliary network to interpolate
  - Input: Sparse ROI temps
  - Output: Dense temperature field
  - Use this as training target

Implementation:
  1. Train interpolation network on HBridge data
  2. Generate pseudo-labels for all pixels
  3. Train main model with dense supervision
  4. Validate on LoadShedding

Pros:
  + Data-driven interpolation
  + No physics assumptions needed
  + Can capture complex patterns

Cons:
  - Interpolation quality uncertain
  - Propagates errors from interpolator
  - Requires additional training


FIX 2: Patch-Based Architecture
--------------------------------
Concept:
  Process local patches, not full image
  Forces model to learn local FLIR → temp relationship

Architecture Change:
  Current: U-Net processes full 480×640 image
  New:     Process 64×64 patches around each component

Implementation:
  1. Extract 64×64 patch centered on each component ROI
  2. Input: FLIR patch + time scalar
  3. Output: Single temperature value (component center)
  4. Train on patches from both PCBs

Training:
  - HBridge: 22 components × 185 timestamps = 4,070 patches
  - LoadShedding: 20 components × ~185 timestamps = 3,700 patches
  - Total: ~7,770 training patches
  - No position information (translation invariant)

Pros:
  + Position-independent learning
  + Can train on patches from both PCBs
  + Naturally generalizes to new positions
  + Smaller model (less parameters)

Cons:
  - Loses global context
  - Can't model long-range thermal coupling
  - Component-level prediction only (no full field)
  - May need larger patches for context


FIX 3: Object Detection Style Architecture
-------------------------------------------
Concept:
  Detect components, predict temp for each
  Like YOLO/Faster-RCNN but for temperature

Architecture:
  1. Backbone: Extract features from full FLIR image
  2. RPN: Detect component regions (given ROI masks)
  3. RoI pooling: Extract features for each component
  4. Head: Predict temperature from component features

Implementation:
  Stage 1: Feature Extraction
    - Input: 480×640 FLIR + time
    - Output: Feature map
  
  Stage 2: RoI Feature Extraction
    - For each component ROI:
      • Pool features from that region
      • Get fixed-size feature vector
  
  Stage 3: Temperature Prediction
    - Input: Component features + time
    - Output: Temperature (single value)

Training:
  - Loss: MSE between predicted and actual temps
  - All components from both PCBs
  - Model learns component-level features

Pros:
  + Uses ROI information explicitly
  + Position-independent component features
  + Can train on multiple PCBs naturally
  + Scales to new component locations

Cons:
  - More complex architecture
  - Requires ROI masks at inference (have this)
  - No full-field prediction
  - May need more training data


FIX 4: Attention-Based U-Net
-----------------------------
Concept:
  Add attention mechanism to focus on relevant features
  Reduce reliance on spatial position

Architecture Changes:
  1. Add self-attention layers in U-Net bottleneck
  2. Learn where to focus for each component
  3. Query: Component location
  4. Keys/Values: FLIR features across image

Implementation:
  Modified U-Net:
    Encoder → Extract features
    Attention → Focus on relevant regions
    Decoder → Generate prediction
    Masking → Only penalize at ROIs

Training:
  - Component-aware attention
  - Learns: "For this component type, look at surrounding pattern"
  - Less position-dependent

Pros:
  + Keeps U-Net structure
  + Adds position-independent learning
  + Can model long-range dependencies
  + Interpretable (can visualize attention)

Cons:
  - More parameters
  - Slower training
  - Still needs masked loss (partial fix only)
  - May not fully solve position problem


FIX 5: Multi-PCB Training with Data Augmentation
-------------------------------------------------
Concept:
  Train on BOTH PCBs with augmentation
  Force model to learn invariant features

Dataset Augmentation:
  1. Spatial: Rotate, flip, translate FLIR images and ROI masks together
  2. Thermal: Add noise, scale intensities
  3. Component: Randomly drop components during training
  4. Mix: Combine patches from different PCBs

Implementation:
  # Training generator
  def augment_sample(flir, rois, temps):
      # Random rotation
      angle = random.choice([0, 90, 180, 270])
      flir = rotate(flir, angle)
      rois = rotate(rois, angle)
      
      # Random flip
      if random.random() < 0.5:
          flir = flip(flir, axis=1)
          rois = flip(rois, axis=1)
      
      # Random crop and resize
      flir, rois = random_crop(flir, rois, size=(384, 512))
      flir = resize(flir, (480, 640))
      rois = resize(rois, (480, 640))
      
      # Thermal augmentation
      flir += np.random.normal(0, 0.5, flir.shape)
      
      return flir, rois, temps

Training:
  - Train on HBridge + LoadShedding simultaneously
  - Apply augmentation to both
  - Forces position invariance

Pros:
  + Uses all available data
  + Augmentation increases diversity
  + Can help reduce position dependence
  + No architecture changes needed

Cons:
  - Augmentation may not be physically valid
  - Rotations change thermal patterns
  - Still limited by sparse supervision
  - Partial solution only


FIX 6: Physics-Informed Neural Network (PINN)
----------------------------------------------
Concept:
  Incorporate thermal physics into loss function
  Ensure predictions obey heat equation

Physics Constraints:
  1. Heat equation: ∂T/∂t = α∇²T + Q
  2. Boundary conditions: Board edges, components
  3. Conservation of energy

Loss Function:
  Total Loss = Data Loss + Physics Loss
  
  Data Loss = MSE at ROI locations
  
  Physics Loss = ||∂T/∂t - α∇²T - Q||²
    + Boundary condition violations
    + Energy conservation violations

Implementation:
  1. Predict full temperature field
  2. Compute spatial/temporal derivatives
  3. Check physics equation residuals
  4. Penalize violations

Pros:
  + Physically consistent predictions
  + Can extrapolate better
  + Dense supervision from physics
  + Generalizes across scenarios

Cons:
  - Requires physics parameters (α, Q, etc.)
  - Much more complex
  - Slower training
  - May not have all physics info


FIX 7: Component-Type Embeddings
---------------------------------
Concept:
  Learn embeddings for component types
  Share learning across similar components

Architecture:
  1. Component metadata: Type, power rating, package
  2. Embedding: Map component type → feature vector
  3. Combine: FLIR features + component embedding → temp

Implementation:
  # Component types
  component_types = {
      'MOSFET': 0,
      'IC': 1,
      'Resistor': 2,
      'Capacitor': 3,
      ...
  }
  
  # Embedding layer
  embedding = nn.Embedding(n_types, embedding_dim=64)
  
  # Forward pass
  flir_features = encoder(flir_image)
  component_emb = embedding(component_type)
  combined = concat(flir_features, component_emb, time)
  temp = predictor(combined)

Training:
  - Components of same type share embedding
  - Model learns type-specific FLIR→temp relationship
  - Can generalize to new positions of known types

Pros:
  + Leverages component type information
  + Transfers learning across instances
  + Can handle new positions of known types
  + Relatively simple addition

Cons:
  - Requires component type labels
  - Fails on unknown component types
  - Still needs position-independent features
  - Partial solution

10. RISK ASSESSMENT
================================================================================

HIGH RISK:
----------
1. Fundamental Architectural Limitation
   Risk: U-Net with masked loss cannot learn position-independent features
   Mitigation: Switch to patch-based or RoI-based architecture early
   Impact: May require complete redesign

2. Insufficient Training Data
   Risk: 2 PCBs insufficient to learn generalizable physics
   Mitigation: Extensive augmentation, collect more PCB data
   Impact: May hit performance ceiling

3. PCB Physics Too Different
   Risk: HBridge and LoadShedding have incompatible thermal behavior
   Mitigation: Component-type-specific modeling
   Impact: May need per-PCB-family models

MEDIUM RISK:
------------
1. Overfitting to Training PCBs
   Risk: Model memorizes training data, doesn't generalize
   Mitigation: Strong regularization, dropout, augmentation
   Impact: Lower cross-PCB performance

2. ROI Quality Issues
   Risk: Inaccurate ROI masks lead to wrong supervision
   Mitigation: Verify ROI alignments, manual correction
   Impact: Reduced model accuracy

3. Temporal Sampling Mismatch
   Risk: Training and deployment thermal conditions differ
   Mitigation: Diverse temporal sampling, steady-state focus
   Impact: Model fails at certain thermal conditions

LOW RISK:
---------
1. Normalization Issues
   Risk: Different temperature ranges across PCBs
   Mitigation: Careful normalization, per-PCB statistics
   Impact: Minor accuracy reduction

2. Computational Resources
   Risk: Training takes too long
   Mitigation: Smaller models, efficient architecture
   Impact: Slower iteration

11. DECISION POINTS
================================================================================

CHECKPOINT 1: After Cross-PCB Baseline (Phase 1)
-------------------------------------------------
Question: How bad is cross-PCB generalization?

If R² > -5:
  → Proceed with current architecture, try augmentation
  
If -5 > R² > -20:
  → Moderate failure, try patch-based approach
  
If R² < -20:
  → Severe failure, major architecture change needed


CHECKPOINT 2: After Temporal Validation (Phase 2)
--------------------------------------------------
Question: Can model learn FLIR→embedded when supervised?

If R² > 0.5:
  → Yes, model capable of learning, problem is generalization
  → Proceed to Phase 3 (patch-based)
  
If 0.0 < R² < 0.5:
  → Partial learning, may need architecture improvements
  → Try both Phase 3 and data quality fixes
  
If R² < 0.0:
  → Fundamental issue: data quality, architecture, or both
  → Deep dive into data analysis before proceeding


CHECKPOINT 3: After Patch-Based Model (Phase 3)
------------------------------------------------
Question: Does position-independent learning help?

If Cross-PCB R² > 0.5:
  → Success! Proceed to optimization
  
If 0.0 < R² < 0.5:
  → Improvement but not enough
  → Try Phase 4 (multi-PCB training)
  
If R² < 0.0:
  → Patch approach insufficient
  → Need Phase 5 (advanced methods)
